# 架构说明

本文说明系统怎么把「取流 → 推理 → 规则 → 告警 → 报告」串起来，以及几个关键取舍。

## 1. 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 前端  Streamlit（app.py / multi_panel.py / edge_panel.py）   │
│  实时监控 · 规则引擎 · 多路监控 · 告警列表 · 报告查看           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 逐帧驱动 / 事件回调
┌───────────────────────────▼─────────────────────────────────┐
│ 编排  LangGraph（graph_def.py）                               │
│  取流 → 检测 → 判断 → 告警 → 报告，条件路由决定是否进告警节点    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│ 推理  ModelService（edge/model_service.py）                   │
│  共享模型池：按权重路径做 key，多路相机只加载一次               │
│  YOLO11s 检测 · YOLO-Seg 分割 · YOLOv8n-pose 姿态             │
└───────────────────────────┬─────────────────────────────────┘
                            │ 统一成 Track（人体框 + 关键点）
┌───────────────────────────▼─────────────────────────────────┐
│ 规则  RulesEngine（edge/rules_engine.py）                     │
│  away · sleep · intrusion · fall · helmet · loiter           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 状态跃迁 normal → suspected → abnormal
┌───────────────────────────▼─────────────────────────────────┐
│ 输出  EdgePipeline + EventDispatcher                          │
│  抓拍存证 · JSONL 落盘 · Webhook 推送 · Markdown 报告          │
└─────────────────────────────────────────────────────────────┘
```

## 2. 一帧的生命周期

1. **取流**：`stream_reader.py` 每路一个线程，按目标帧率降采样，只保留最新帧；断流按 1→2→4→8→16→32→60 s 退避重连。
2. **推理**：`ModelService.process(cam, frame)` 调姿态模型，输出人体框 + 17 个关键点；`keypoint_bbox` 把关键点转成稳健的人体框。
3. **跨帧关联**：ByteTrack 给每个人一个 `track_id`，ID 丢失时用 Re-ID（OSNet）在 120 px / 3 s 窗口内恢复。
4. **场景叠加**：按相机 `scene` 决定是否再跑安全帽检测、火灾分割，结果回写进 `Track`（`has_helmet`、`fire` 事件）。
5. **规则判定**：`RulesEngine.update(tracks, now)` 逐条规则更新状态机。
6. **状态跃迁**：只有 `normal → abnormal` 的那一帧才建档上报；`suspected` 只更新画框颜色。
7. **去重**：同一 `(相机, track, 规则)` 30 秒内不重复；同一相机同一规则下，最近 30 秒内所有已报框都参与 IoU 比对，避免多人互相覆盖导致刷屏。
8. **输出**：`_mint_identity` 裁剪告警框、生成事件 ID、写抓拍图，`EventDispatcher` 入有界队列（50）异步消费。

## 3. 五条规则

| 规则 | 输入 | 判定 | 默认阈值 |
|---|---|---|---|
| helmet | 人体框 + 头框 | 头框中心落在人体框内、类别为 `no-hardhat` | conf 0.40，稳定器 2 帧 |
| fire | 分割掩码 | `fire`/`smoke` 命中且面积占比达标 | conf 0.15，连续 1 帧 |
| sleep | 关键点 | `(nose.y − 肩中点y) / 肩宽 > −0.32` | 连续 40 帧（演示）/ 300 帧 |
| away | ROI 内人体数 | ROI 内无人累计时长 | 60 s 疑似 / 180 s 确认 |
| loiter | track 位置序列 | ROI 内停留时长或折返次数 | 8 s 疑似 / 20 s 确认 / 折返 2 次 |

规则之间互斥顺序：`away → sleep → intrusion → fall → helmet → loiter`。离岗成立时暂停睡岗判定，避免空岗空报警。

## 4. 配置体系

四份 YAML 与代码解耦：

- `scenes.yaml`：每个场景的模型路径、输入尺寸、置信度、类别、后处理参数（稳定器、面积过滤、关键点阈值）。
- `cameras.yaml`：相机 → 场景绑定、ROI 多边形、RTSP 地址、回退视频。
- `rules.yaml`：每条规则的时间阈值、冷却、告警级别、演示模式阈值。
- `system.yaml`：全局取流参数、重连策略、告警 webhook、运行环境。

所有 `source` 支持 `${VAR:默认值}`，现场部署用环境变量覆盖，不把账号写进仓库。

## 5. 关键取舍

**为什么共享模型池？**
同一权重被多路相机引用时只加载一次。四路并行时显存从「每进程一份」降到「全局一份」，这是四路能跑到 41 FPS 的前提。

**为什么一次姿态推理供三条规则？**
睡岗、离岗、徘徊本质都在看人的位置与姿态。分开推理会把姿态模型跑三遍，帧率直接掉一半。

**为什么按 `scene` 分派规则？**
早期版本所有规则无条件运行，Camera_01 的危险区 ROI 会被徘徊规则当成逗留区误触发。改成每路相机声明自己的场景后，误报消失。

**为什么告警框要存一个列表？**
最初每个 `(相机, 规则)` 只记最后一个告警框，A 报完 B 一报就把 A 的框覆盖，A 隔几帧再被判 abnormal 又能通过，导致同一批人反复上报。改成 30 秒窗口内所有框参与 IoU 比对后，四路告警数从 3/3/1/1 降到 2/1/0/0。

## 6. 性能与局限

- 单模型 7 ms，三模型同驻 11 ms，四路并行均摊 24.3 ms/帧（41 FPS）。
- TensorRT engine 绑定 GPU 与 TRT 版本，换机器需重新导出。
- 近景两人头部紧挨时，端到端模型可能给出合并大框，目前靠人体框约束与显示层抑制缓解；彻底解决需要人体检测裁头。
